# Troubleshooting

Common failures when running Arknights: Endfield through the patched CrossOver build, and what to do about them. For deeper engineering detail, follow the links into the research docs. To capture logs for a bug report, see [Debug logging](installation.md#debug-logging) in [installation.md](installation.md).

## Setup & deployment

- **"CrossOver.app is version X, expected 26.3"** — the swap needs a matching Wine ABI. Install CrossOver 26.3.
- **"CrossOver_Endfield_Patch is damaged and can't be opened" (over and over) / binaries killed with exit 137** — the patched bundle's signature seal is missing or broken. Click **Cancel** (not *Move to Trash*), then re-run `./scripts/swap-into-crossover.sh`, which re-seals it (it moves an old copy macOS won't let it delete to the Trash). If you edited files inside the patched app by hand, re-seal it: `codesign --force --sign - --preserve-metadata=entitlements /Applications/CrossOver_Endfield_Patch.app`. Details: [05-swapping-into-crossover.md → Verified recipe](05-swapping-into-crossover.md#verified-recipe-2026-09-crossover-2620--macos-270--m4).
- **ACE "driver error 13" comes back** — the patched `ntdll.so`/`ntoskrnl.exe` aren't loading; verify the swap paths and that you launched the *patched* app.
- **Clicking a bottle's program (or an old `Arknights Endfield.app`) opens the *stock* CrossOver** — CrossOver bakes the creating app's bundle identifier into every program stub it generates, so anything created before patching stays bound to the stock app. Quit both apps, delete the stubs under `~/Applications/CrossOver/…`, then create the bottle and install the launcher **from `CrossOver_Endfield_Patch.app`** (the Patcher's **Automated Setup…** does this).
- **A Windows program in the *patched* CrossOver returns `11`, with only the two `msync:` lines in the CrossOver error dialog** — those two lines are normal wineserver startup output (they appear on successful runs too), so the dialog has truncated the useful part. Run the same program through the patched app's wine from Terminal to see the real error:
  ```bash
  CXR="/Applications/CrossOver_Endfield_Patch.app/Contents/SharedSupport/CrossOver"
  "$CXR/bin/wine" --bottle "Arknights Endfield" --wait-children --debugmsg err+all -- ~/Downloads/GRYPHLINK_*.exe
  ```
  Status `11` is what macOS reports for a process killed by `SIGSEGV`, so this is a Wine-side crash rather than an installer error. Include your macOS version and the exact CrossOver build (`defaults read /Applications/CrossOver.app/Contents/Info.plist CFBundleVersion`) in a report — CrossOver point builds that all say `26.3` can ship different Wine modules — and cross-check with the previous FineWine release if one worked.
- **The Gryphline launcher opens and then immediately closes when started from the CrossOver app's bottle *Start* button** — the launcher's **Chromium/QtWebEngine renderer** (`QtWebEngineProcess.exe`) crashes on that GUI path. It's unrelated to the ACE fixes, and **no bottle setting fixes it** (MSync off, High Resolution off, other graphics backends, GPU flags, and `--single-process` were all tested and still crash). **It *does* stay up via the direct `wine --cx-app` path**: run `Launcher.exe` through it instead (command in [installation.md §5](installation.md#5-run-the-game); details in [15](project-information/15-launcher-qtwebengine-crash.md)). To start the game *directly* (bypassing the launcher, once installed), use `scripts/launch-endfield.sh`.
- **Game stopped launching after a late-2026 update — log ends in `err:ntoskrnl:KeBugCheckEx 65636157 0 0 0 0`** — the game replaced `ACE-BASE.sys` with a new `ACE-CORE*.sys` driver that aborts during `DriverEntry` (not a missing-export crash). **Fixed** by the `ace-core/0001–0014` patches; the game now launches and is playable. See [14-ace-core-regression.md](project-information/14-ace-core-regression.md) and issue [#43](https://github.com/stoicswe/Endfield_FineWine/issues/43). Capture a failure log with `scripts/01-capture-failure.sh` (use `WINEDEBUG=+ntoskrnl,+module,+loaddll`).
- **The game runs, but the log shows `err:ntoskrnl:KeBugCheckEx 65636154 0 0 0 0` and both ACE-CORE services report `STOPPED`, exit code `1067`** — **harmless for gameplay.** `65636154` decodes to `"Tace"`; ACE-CORE arms its process/thread/image callbacks (**all stubs in Wine**) and a background watchdog waits 1 s for the event, then bug-checks `ExitProcess()`-ing its `winedevice` host. The SCM sees the aborted host as `STOPPED`/`1067` (`ERROR_PROCESS_ABORTED`). The user-mode ACE process is separate and stays connected, so the game plays normally — but the kernel component is *not* actually running. Analysis and an experimental fix (`ace-core/0015`): [14-ace-core-regression.md §13.9](project-information/14-ace-core-regression.md).
- **The launcher opens inconsistently, then crashes and leaves `winedevice`/`.exe` processes behind** — on Apple Silicon this can be the Rosetta/ACE timing path interacting with MSync, especially with D3DMetal. Force-quit the leftover Wine processes, then re-apply the bottle with MSync disabled and retry:
  ```bash
  MSYNC=0 BACKEND=d3dmetal UPDATE=1 ./scripts/create-bottle.sh
  ```
  If the problem started after switching to DXMT, also test the known-stable fallback: set the bottle backend to D3DMetal, launch the game in Vulkan, and do not run the XXMI DirectX 11 path. If disabling MSync does not help, capture the failure with [`scripts/01-capture-failure.sh`](../scripts/01-capture-failure.sh) before reopening the issue; repeated `c0000005` nested exceptions ending in a stack overflow point to the Wine/ACE timing path rather than graphics settings.
- **Start programs from the CrossOver window**, not from the per-program app stubs CrossOver creates in `~/Applications/CrossOver/` (also what Spotlight/Launchpad find). Those stubs' signatures don't verify (`codesign`: "code has no resources but signature indicates they must be present"), so macOS can report them as damaged.
- **GRYPHLINK isn't listed in the bottle** (CrossOver shows only "Uninstall GRYPHLINK") — the launcher's shortcuts weren't registered with CrossOver's menus (seen after installing the launcher from the command line). Re-register them, then reopen the bottle's page: `/Applications/CrossOver_Endfield_Patch.app/Contents/SharedSupport/CrossOver/bin/cxmenu --bottle "Arknights Endfield" --install`.

## In-game graphics

- **DXMT: enabling DLSS turns the scene black, with `NGX: missing evaluation parameter Color`** — CrossOver 26.3's bundled DXMT 0.80 cannot retrieve textures stored through NGX's `SetVoidPointer` as D3D resource pointers. Use **TAAU** or **AMD FSR3** with that build. A DXMT build containing the fix proposed in [3Shain/dxmt#235](https://github.com/3Shain/dxmt/pull/235) can run DLSS upscaling through MetalFX; see [stock and patched DXMT builds](technical.md#dlss-under-dxmt-stock-and-patched-builds). FineWine 1.2.3 alone does not replace DXMT with a fixed build.
- **White / blank screen (very common after a game update)** — the game shipped an update that reset its renderer to **DirectX 12**, which does not work under CrossOver 26.3 (`vkd3d` can't compile the game's DXIL/SM6 shaders → `Cannot load DXIL conversion library`). **Fix: run the game in DirectX 11** — start it with the launcher's **Launch with DirectX 11** (dropdown next to the Start button; the plain Start button uses the default renderer), or launch Unity with `-force-d3d11`. DirectX 11 uses the mature D3DMetal/DXMT path. **Vulkan also works** through the patched MoltenVK the Patcher bundles ([graphics-performance.md](graphics-performance.md#the-vulkan-renderer)). Do **not** try to fix this by overwriting CrossOver's `d3d11/d3d12/dxgi.dll` with the `apple_gptk` copies — that breaks `unityplayer.dll` init (Windows error **1114**); those D3DMetal DLLs are only meant to be loaded through CrossOver's own backend mechanism. Background: [graphics-performance.md](graphics-performance.md).
- **Vulkan mode: logged out with every app closed after teleporting to Snowy Forest** — a GPU hang that makes macOS kill WindowServer ([#22](https://github.com/stoicswe/Endfield_FineWine/issues/22)). The patched MoltenVK bundled by the Patcher fixes this; with an older/stock MoltenVK, play that area in DirectX 11.
- **Vulkan mode: bushes/grass render as odd, stretched polygons (or blocky lines) after updating the patched MoltenVK** — the game's Vulkan pipeline cache is stale. `…/LocalLow/Gryphline/Endfield/vulkan_pso_cache.bin` holds the MSL/pipelines MoltenVK compiled under the *previous* module build; once the modules change (or `MVK_CONFIG_USE_METAL_ARGUMENT_BUFFERS` changes), the game can reuse entries that no longer match and draw meshes with wrong shader/descriptor data. **Fix (manual):** quit the game, delete the cache, and let it rebuild:
  ```bash
  rm "$HOME/Library/Application Support/CrossOver/Bottles/Arknights Endfield/drive_c/users/crossover/AppData/LocalLow/Gryphline/Endfield/vulkan_pso_cache.bin"
  ```
  The next launch is slower while pipelines recompile (same cold-cache behaviour as the shader warm-up). Only the Vulkan renderer is affected — DirectX 11 is not. This project deliberately does **not** delete the cache automatically.
- **Vulkan mode: a few pipelines fail to compile (`VkShaderModule … 'sampler' attribute parameter is out of bounds: must be between 0 and 15`)** — MoltenVK binds descriptors for **push-descriptor** sets individually (Metal argument buffers are disabled for them), so a shader using more than 16 combined image samplers exceeds Metal's 16-slot limit and its pipeline isn't created. These are usually unused material permutations; if a visible object is missing or black, this is the cause. (Upstream MoltenVK limitation; visible with `MVK_CONFIG_LOG_LEVEL=3` in a `diagnose-vulkan.sh` capture.)
- **`unityplayer.dll` "missing or corrupt" (error 1114)** — a DLL-init failure, usually from swapping graphics DLLs (see above) or launching `Endfield.exe` directly without the launcher's working directory. Restore CrossOver's default `d3d11/d3d12/dxgi.dll`, and launch via the Gryphline launcher.
- **High Resolution Mode** (the bottle's Advanced Settings) renders a white screen — leave it off ([#2](https://github.com/stoicswe/Endfield_FineWine/issues/2)).
- **Black screen on later launches** — reported in [#2](https://github.com/stoicswe/Endfield_FineWine/issues/2); the reporter's workaround was to delete the game's registry data (`HKCU\Software\Gryphline\Endfield` and `…\Gryphline\sdk_data\…` — settings and login cache, e.g. via CrossOver → *Run Command* → `regedit`) and log in again. That resets the in-game settings.

## General

- **Two copies of the game running** — e.g. a direct `launch-endfield.sh` start plus one from the launcher. They fight over the same files ("The process cannot access the file…" in `Player.log`); quit both and start one.
- **Freeze with sound still playing on a 16 GB Mac** — the memory-pressure freeze described in [14-performance-on-16gb-macs.md](14-performance-on-16gb-macs.md); force-quit, free memory, relaunch.
- **Something else?** Capture a failure log with [`scripts/01-capture-failure.sh`](../scripts/01-capture-failure.sh) and open an issue. How the capture loop was used to find the original failure: [10-milestone-1-results.md](10-milestone-1-results.md).
